2026年10月21日 明确目标与疑问

我这次想实现什么

现在我已经有Jetson、MID-360和Point-LIO的扫描设备。接下来，我想慢慢尝试让设备实时扫描周围环境，有物体靠近时可以通过震动提醒我。我先问需要学习哪些内容，希望弄清楚实现这件事的路径。

我已经会什么

我会写ROS 2节点，所以这次也想弄清楚ROS 1的节点是更简单还是更难。对照两者的接口后，我发现订阅、回调和发布的基本思路可以沿用，主要是换接口。对于这次功能，我需要重点弄清楚的是点云处理和提醒判断，而不是把节点知识从头再学一次。

老师给我的建议

老师建议根据物体距离的远近，改变震动的强弱。我觉得这个初步想法蛮好：物体越近，提醒越明显。我也考虑过通过改变震动间隔来传递距离信息，不过目前更想先围绕老师建议的强弱变化继续思考。具体分几档、从多远开始提醒，现在还没有定。

我对最近点的疑问

最开始我想到，可以直接取所有点中最近的一个来判断距离。但继续考虑后，我发现这样可能把支架、地面或偶发噪声当成近处障碍。所以我想弄清楚，除了直接取最小值，还有哪些选择办法。关键不是不关心最近的障碍，而是不能让一个尚未确认是否可靠的点决定全部提醒。

我正在考虑的候选办法

查阅资料后，我整理出几种可以比较的办法：先筛出关注的空间区域；检查近点周围有没有其他点支持；把点分成点群后，比较最近的可信表面；或结合短时间内的连续观察。这些目前都还在考虑中，我还没有选定具体方法，也没有写进代码或完成验证。

我还需要注意，不能把过滤条件设得太强。细杆或其他小物体可能只有少量点，不能因为点少就直接忽略。距离过滤和连续确认也可能增加漏报或延迟，后面需要用实际数据比较。

我怎样安排文件

prototype_running; obstacle_detection_not_implemented; motor_control_disabled

这条文本只表示原型节点运行中、障碍检测尚未实现、马达控制关闭，不是测量距离，也不是实际震动指令。这个程序目前没有订阅雷达或控制任何硬件。

2026年10月21日 我怎样复现这一步

建立包的过程

下面记录的是从空目录建立时的操作。现在同名工作空间已经做好，不需要覆盖重建；我可以先查看源码和运行节点，真正练习时另建haptic_practice_ws与haptic_practice包。

source ~/mid360_pointlio_ws/devel/setup.bash
mkdir -p ~/haptic_ws/src
cd ~/haptic_ws/src
catkin_create_pkg haptic_feedback rospy std_msgs
mkdir -p haptic_feedback/scripts haptic_feedback/launch

接着编写scripts/haptic_feedback_node.py和launch/bringup.launch，在CMakeLists.txt中使用catkin_install_python登记脚本，再给脚本执行权限并构建。Python不需要编译成二进制，但首次仍要让catkin生成包环境与执行入口。

chmod +x ~/haptic_ws/src/haptic_feedback/scripts/haptic_feedback_node.py
cd ~/haptic_ws
catkin_make -j2
source devel/setup.bash

运行已经建立好的节点

在Jetson终端A运行下面两行。roslaunch会在需要时启动默认master；这个launch只启动新节点，不启动雷达和Point-LIO。

source ~/haptic_ws/devel/setup.bash
roslaunch haptic_feedback bringup.launch

另开终端B，先加载同一环境，再检查节点与消息。rostopic hz观察几秒后按Ctrl+C退出；要停止节点，则在终端A按Ctrl+C。

source ~/haptic_ws/devel/setup.bash
rosnode list
rosnode info /haptic_feedback_node
rostopic echo -n 1 /haptic/status
rostopic hz /haptic/status

我需要记住的区别

haptic_feedback是包名，haptic_feedback_node是运行中的节点名，/haptic/status是topic。rosrun只运行脚本，需要已有master；roslaunch可以启动所需master。新工作空间没有加入终端自动加载，所以每次使用它前仍要source。不要同时重复启动同名节点。

完整的源码说明、CMake与launch解释、rosrun的双终端用法，以及另建练习包的步骤，保存在~/haptic_ws/README.txt。测试记录在~/haptic_ws/logs/20261021。

2026年10月21日 我选择先做周围一圈的感知

在开发范围的选择中，我更希望先尝试B，也就是身体周围一圈的障碍感知，之后再加入C的方向区分。如果尝试失败或处理起来太困难，再退回A，只做前方的检测。我不希望一开始就把目标限制在前方，但也保留缩小范围的办法。

这里的B是我希望实现的覆盖目标，不代表现在的穿戴方式已经能无盲区地看到一整圈。下一步我需要先说清楚雷达装在身体的哪个位置、朝向如何，再观察真实点云里身体和装置自身出现在什么地方。安装位置还没有在这轮讨论中确认，因此暂不设定自身排除区域、检测高度或距离阈值，也不修改代码。

另外，我弄清楚了持续显示话题的命令区别：rostopic echo -n 1 /haptic/point_count只读一条就退出；去掉-n 1后才会持续打印收到的消息。这轮只是解释用法，没有远程更改终端B当前的命令。

2026年10月21日 胸前安装与雷达视场限制

我计划把MID-360放在胸前，也明确提出设计时必须考虑这款雷达的角度限制。查阅Livox官方快速入门指南后，我确认其水平视场为360°，垂直视场为59°，标准正放时相对雷达水平面约为向下7°到向上52°。这不是上下对称的视场，更不是整个球面都能看到。

由这个视场和胸前安装位置，我考虑到两类限制。第一，身体会遮挡一部分后方视线，因此不能把标称水平360°写成穿戴后无盲区的周向感知。第二，如果正放且水平安装，向下只有约7°的覆盖，近处的低矮障碍可能落在视场外。后续必须根据实际高度、朝向和点云观察确认，不能把没有点误认为没有障碍。软件筛选或Point-LIO不能凭空恢复当前未测到的障碍。

我仍保留先尝试B、之后增加C、困难时退回A的顺序，但把第一阶段理解为实际可见范围内的周向检测，而不是保证身体周围无盲区。这次只确认胸前位置，正放、倒放或倾斜方式尚未选择；下一步先确认朝向与安装高度，不改代码、驱动或Point-LIO的外参。参考：https://dl.djicdn.com/downloads/Livox/Mid-360/QSG/Livox_Mid-360_Quick_Start_Guide_multi.pdf，第5页。

继续考虑胸前安装后，我把当前设计重点进一步明确为：在承认盲区的前提下，用一个MID-360尽可能覆盖前方需要关注的范围。我还没有选定安装倾角，希望把身体晃动和各种误差一起考虑，而不是只看站直不动时的理想视场。先前关于周向检测的讨论保留为探索过程，当前先围绕前方覆盖展开设计，未来方向区分仍可以继续研究。

我计划最终把雷达放在胸前，把电脑和电池等放在后背。显示器是否集成到研究装置里还在考虑；作为开发者，我需要能够查看状态和点云，但产品形态不打算带显示器。开发时可继续使用已有的无线桌面作为一种查看途径，不过它是否适合长期调试、走动时网络是否稳定，还需要验证。

在选择倾角前，我需要先知道雷达光学中心离地高度、希望最早提醒的水平距离，以及需要覆盖的最低和最高障碍高度。仅凭59°垂直视场，不能直接选出一个对所有情况都最好的安装角度。在前向竖直截面的简化模型里，正放雷达向前下倾alpha度时，前向俯仰覆盖约为-7-alpha度到52-alpha度；这是几何推算，不是穿戴实验结果，也不能代表倾斜后所有方位的覆盖。

我考虑把静态安装角和走路时的姿态变化分开。身体前后俯仰、左右侧倾以及绑带松动，都可能改变有效覆盖。如果以后得到姿态估计，可以将已经测到的点转换到统一参考系，但这不能补回视场外或被身体遮挡的物体。姿态估计误差、时间同步和处理延迟也需要纳入测试，不能把姿态补偿等同于消除盲区。

接下来我想比较三种需求：优先近处低矮障碍、优先胸部和头部高度障碍，或者明确规定距离后兼顾两者。最终选择需要由我继续决定，并通过静止及走动时的数据验证。目前没有选择倾角，没有设定误差裕量，也没有改动节点、驱动、Point-LIO外参或安装结构。下一步先补充安装高度，再确定希望覆盖的目标区域。
